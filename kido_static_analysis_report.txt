1. EXECUTIVE SUMMARY
================================================================================================
* kido.sample is a 32-bit Windows DLL (PE32, i386, GUI subsystem), 86,431 bytes: an 86,016-byte
  PE image plus a 415-byte HTML trailer. No exports, no resources, 42 imports.

* It is a WRAPPER, not the worm itself. Three nested layers were recovered statically:

    Stage 1  The file. An obfuscated reflective loader ("crypter"). Its .data section (57 KB,
             entropy 7.48) holds a 42,496-byte encoded DLL. The code decodes it, maps it into
             memory by hand (VirtualAlloc / LoadLibraryA / GetProcAddress / VirtualProtect) and
             calls its entry point with DLL_PROCESS_ATTACH.
    Stage 2  A UPX-packed DLL (sections UPX0 / UPX1 / UPX2, UPX 1.x stub, NRV2B-LE32).
    Stage 3  The decompressed 102,159-byte image of the real malware, a Conficker worm DLL.
             Its plaintext strings and imports show: MS08-067 style SMB/RPC exploitation, a
             payload-serving HTTP server, UPnP port mapping, domain-generation rendezvous,
             a scareware download, svchost "netsvcs" service persistence, System Restore
             reset, process-injection APIs and a Ukraine-avoidance check.

* PACKED: YES.   ENCRYPTED: YES (hard-coded XOR keystream, recoverable).   OBFUSCATED: YES (heavy).
  Evidence is in section 2; the mechanisms are in sections 6 and 7.

* The decoding is bit-exact: the Adler-32 of the decoded compressed stream and the Adler-32 of
  the decompressed image both match the values stored in the UPX pack header.

* The unpacked strings match public descriptions of Conficker variant A item by item: 5-TLD
  domain generator, the three IP-lookup sites, the six date-lookup sites, the
  trafficconverter.biz/.../loadadv.exe download, GeoIP + keyboard-layout Ukraine avoidance, UPnP,
  netsvcs service (section 8.4).

* Stage 3 was rebuilt exactly as the UPX stub would (section 8.2) and disassembled; the behaviours
  read in the code are in kido_program_flow_pseudocode.txt and tagged CODE in section 9.2. They
  include an RSA-1024 signature gate (e = 50001) that only lets payloads signed by the operators run.
  capa 9.2.1 finds NO capability in the file as received (the obfuscation defeats it) but 70 rules
  in the rebuilt stage 3, and every hit agrees with the manual analysis (section 9.1).

* NOT established: anything about run-time behaviour (nothing was executed); the origin of the
  7,424-byte random block (characterised as dead data, most likely build-time padding, 6.7) and of
  the 415-byte HTML trailer; the propagation, name-generation and UPnP internals, which are only
  summarised on purpose. kido.zip was skipped as requested.

2. IS IT PACKED, OBFUSCATED OR ENCRYPTED?   (direct answer)
================================================================================================

   PACKED = YES          ENCRYPTED = YES          OBFUSCATED = YES          (all three, in layers)

2.1 PACKED - YES (two nested layers)
    Layer A, the file itself - a custom crypter / reflective loader.
      Not a commercial or well-known packer: TrID and a 4,462-signature PEiD-format database
      find no packer signature (the entry point is genuine MSVC DLL start-up code, 6.5) and the
      section names are ordinary (.text .rdata .data .reloc). The packing is structural:
        - .data is 57,344 bytes (66% of the file), entropy 7.48, with no readable content;
        - the import table is tiny (42 imports) and holds the classic loader set VirtualAlloc /
          VirtualProtect / LoadLibraryA / GetProcAddress;
        - the code maps a hidden PE image out of .data and calls its entry point (6.9).
    Layer B, inside - the hidden DLL is UPX-packed: sections UPX0/UPX1/UPX2, "UPX!" pack header
      (format 9 = win32/pe, method 2 = NRV2B-LE32, level 9), UPX DLL stub at the entry point.
      39,670 compressed bytes expand to 102,159 bytes (38.8%).

2.2 ENCRYPTED - YES (encoded with an embedded, position-dependent XOR keystream)
    The 42,496-byte stage-2 DLL is stored in .data as  plaintext XOR keystream(address),  and
    the 4-byte units inside every 256-byte block are additionally scrambled (offset XOR 0xDC).
    Its MZ word and "PE\0\0" signature are erased. There is no external key - every constant is
    inside the file - so this is obfuscation-grade, not cryptographic, protection. I recovered
    it statically and confirmed the result with UPX's own Adler-32 values (6.10).
    A further 7,424 bytes of random-looking data follow the image in .data. No stage-1 code
    references them; they are dead data, most likely build-time padding (6.7).

2.3 OBFUSCATED - YES (heavy; stage-1 code and headers)
    - Scattered control flow: 177 JMPs in 3,263 instructions - 65 indirect through a 65-entry
      code-pointer table in .data, 4 through a second table - and only 7 RETs. There is no
      recognisable function structure apart from the CRT start-up.
    - 67 inlined copies of the same encoded-array accessor (no helper function), driven by
      constants kept in writable memory (opaque constants).
    - Junk code: 90 x87 instructions whose results go to scratch variables nobody reads; about
      50 of the 58 API call sites are decoys; decoy imports from ctype / math / security APIs.
    - Header hygiene: Rich header zeroed, implausible timestamps, import descriptors without an
      OriginalFirstThunk, signatures of the embedded image erased.
    - Tool corroboration: capa 9.2.1 reports "no capabilities found" for the file (Vivisect finds
      only 11 functions), and DiE 3.10 flags .data (entropy 7.48) as packed (6.5, 9.1).
    NOT present in stage 1: anti-debugging, anti-VM, SEH tricks, TLS callbacks, self-modifying
    code, per-string encryption. (Stage 1 holds no meaningful strings at all; the hiding is done
    by the layering.)

2.4 Where the strings went
    kido.sample itself contains no URLs, IPs, registry keys, mutexes or file paths (6.6). They
    live in layer 3 and are plaintext once layers 1 and 2 are undone (section 8).

3. SCOPE, METHOD, TOOLING, EVIDENCE LEGEND
================================================================================================
Rule followed : the sample was only ever read as data. Nothing was run, debugged or loaded. The
                analysis VM that the user provided (VMware guest on the analyst's PC, Windows 11,
                bridged to the home LAN) was used ONLY to run static tools on copies of the files;
                the sample was never executed there.
Tools used    : pefile 2024.8.26; Capstone 5.0.7 (disassembly); TrID 2.47; PEiD-format signature
                database from ExeinfoPE (userdb.txt, 4,462 signatures, used as data only);
                GNU strings; YARA 4.3.2 (pe and math modules); Python 3.12 run in isolated mode
                (-I) from outside the sample folder, scripts kept in a separate scratch folder.
                On the VM (C:\Tools): capa 9.2.1 (standalone, Vivisect backend) and Detect It Easy
                3.10 (diec), both run over SSH on the sample and on the rebuilt stage-3 PE (9.1).
NOT used      : FLOSS - installed but deliberately not run: its decoding stage emulates code.
                No debugger, sandbox, FakeNet-NG, Procmon or Regshot: those need execution.
How layers 2/3 were obtained:
                I re-implemented, in Python and on in-memory copies, (a) the decode routine found
                in the stage-1 code and (b) the documented UPX NRV2B-LE32 decompressor. No sample
                code was executed. Transient copies of the decoded layers were written to the
                session scratch folder (outside the project) only to test the YARA rules, and
                were deleted afterwards. For capa / DiE the rebuilt stage 3 was written out as a
                standalone PE (9.1) and copied, with the sample, to a work folder on the VM under
                non-executable names (.bin / .sample). The VM copies were deleted after the run and
                neither file is in the project folder, which holds this report, the flow document
                and the strings inventory.
Web research  : the SRI / USENIX Conficker analysis was consulted to corroborate attribution
                (section 15). The primary USENIX URL failed; the content was read from the
                static.usenix.org mirror by a web-fetch helper, so [PUB] items are second-hand.

6.7 Trailer and unexplained data  [DATA]
  Trailer (file 0x15000, 415 bytes): a minimal HTML page:
      <!DOCTYPE html PUBLIC "-//W3C//DTD HTML 4.01//EN" ...>  <META HTTP-EQUIV="Refresh"
      CONTENT="0.1"> <META HTTP-EQUIV="Pragma" CONTENT="no-cache"> <META HTTP-EQUIV="Expires"
      CONTENT="-1"> <TITLE></TITLE> <BODY><P></BODY>
  It is outside the image and ignored by the PE loader. No layer contains matching HTML (the worm's
  strings have none), no code emits it, and the worm's own handling of "data after the PE image"
  (a geo-database candidate, flow document 3.7) cannot use it. Origin: most consistent with a
  collection / transport artefact, for example a gateway's meta-refresh page appended to the
  download [INF]; deliberate padding is the alternative. When comparing copies, hash the PE-image
  portion (4.1), which excludes it.

  Random block (file 0x10688..0x12387, 7,424 bytes = 29 x 256): entropy 7.976, chi-square 240
  (random is ~255 +/- 23). Tests run on it, all negative:
    (a) uniformity: each of its 29 sub-blocks has entropy 7.07..7.32 per 256 bytes (random: ~7.2) and
        155..176 distinct byte values (random: ~162); no repeated 8-byte windows;
    (b) no magic numbers (MZ, PE, UPX!, gzip, zlib, bzip2, 7z, RAR, ZIP, CAB, GeoIP, HTML, JPEG, PNG,
        ELF) in the raw block or in five decodings with the image keystream (continuing array 1;
        own array with logical origin 0, 0xA500, 0xC300 and 0x10000);
    (c) no zlib / raw-deflate / gzip / bzip2 / lzma / UPX-NRV2B stream decodes from it; the three short
        deflate "hits" in decoded variants have repetitive low-entropy output (chance artefacts);
    (d) not an LCG byte stream: exhaustive seed search for the MSVCRT, ANSI/glibc, Borland, Numerical
        Recipes, Delphi and VAX generators (byte = bits 0-7, 8-15 or 16-23 of the state, raw and
        decoded block): no match. The top-byte variants (Numerical Recipes, Delphi: byte = bits 24-31)
        were searched over the full 32-bit seed space: no match either;
    (e) reachability: no stage-1 instruction addresses it, and the loader's read range is bounded by
        the headers of the image it maps (highest byte read: logical 0xA5FF), so nothing in stage 1
        consumes it. Its size is a whole number of the 256-byte blocks of the address scramble, but
        the image already ends on a 256-byte boundary, so it was not needed for alignment.
  Conclusion: dead data. Most probably build-time junk padding (per-build variation or dilution of
  static signatures). It is not a second payload, key or configuration that any layer reads. Its exact
  generator is not determinable statically; comparing it with other builds would show whether it varies
  per build.

6.9 Loader flow reconstructed from code  [CODE]
  1. 0x434B   Standard MSVC CRT entry; reason-code dispatch; calls DllMain (0x4110).
  2. 0x4110   DllMain builds the stack constant pool and jumps into the scattered blocks.
  3. 0x1D03   Array base:  lea ebx,[eax*4 + 0x10006088]  ->  [0x10013720]
              (eax = [0x1001321C], which is zero in the file, so base = .data+0x88).
  4. (many)   Header parsing of the embedded image through the accessor, with PE field offsets
              used as constants: e_lfanew (0x3C), SizeOfOptionalHeader (NT+0x14), optional header
              (NT+0x18), AddressOfEntryPoint (NT+0x28), ImageBase (NT+0x34), section header
              size 0x28, section Characteristics (+0x24), page rounding 0xFFF/0x1000.
  5. 0x1B40 / 0x1BC7 / 0x19CE  Memory:  VirtualAlloc(preferred base, image size, MEM_RESERVE
              0x2000, PAGE_NOACCESS), then commit calls VirtualAlloc(base + offset, size,
              MEM_COMMIT 0x1000, protection) for the headers and the sections (the call at
              0x19CE uses PAGE_READWRITE).
  6. 0x1D4B   Copy: decoded bytes are stored one by one (mov [eax+ecx], dl).
  7. 0x2C98 / 0x1677 / 0x1027  Imports: LoadLibraryA(base + descriptor.Name); GetProcAddress by
              name (base + thunk RVA + 2, i.e. skipping the IMAGE_IMPORT_BY_NAME hint) or by
              masked 16-bit ordinal (and eax,0xFFFF); result stored in the IAT slot.
  7b. 0x1758 / 0x32F8  Relocation: stage 1 and stage 2 share ImageBase 0x10000000, so that address is
              normally taken by stage 1 itself and stage 2 lands elsewhere. For every WORD entry of
              the relocation directory the loader takes type = entry >> 12 (shift count 12 is kept in
              the opaque variable .data+0xD0BC) and, for type 3 (HIGHLOW), adds (actual base - preferred
              base) to the dword at page + (entry & 0xFFF) (mask 0xFFF in .data+0xD0E0).   [CODE]
  8. 0x236A   VirtualProtect per section, protection derived from the IMAGE_SCN_* flags
              (code at 0x1D5F maps the "writable" flag 0x80000000 to 0x40 / 0x20).
  9. 0x1708   Hand-off: push lpvReserved; push 1 (DLL_PROCESS_ATTACH); push base;
              add eax,ecx (base + AddressOfEntryPoint); call eax; ... ret 0Ch.
  Result: stage 2 is mapped into the host process, rebased if necessary, and its entry point runs.
  Nothing else of note happens in stage 1.

6.10 Encoding scheme of the embedded image, and how it was verified  [CODE][DATA]
  Accessor semantics (logical byte index i inside the embedded image):
      d    = little-endian dword at  file[0x6088 + ((i & ~3) ^ 0xDC)]
      t    = (((i & ~3) >> 2) | 0x0A0A0082) << 1                          (mod 2^32)
      key  = (t XOR C1) - C2                                              (mod 2^32)
      byte = ((d XOR key) >> (8 * (i & 3))) & 0xFF
      C1 = dword @ file 0x6068 = 0xC41972EB      C2 = dword @ file 0x603C = 0x86E61B46
      (shift counts 2, 1 and 8 are read from .data+0xD0C0, +0xD104, +0xD0C8)
  Observations that pin the scheme down:
    - The first dwords of the array (file 0x6088: 3F 58 27 49 41 58 27 49 ...) are exactly the
      keystream of zero plaintext for logical address 0xDC - i.e. zero padding of the DOS-header
      gap, which also explains the stray "X'I" pattern seen by strings.
    - Decoded logical bytes 0x4E.. read "This program cannot be run in DOS mode.", followed by a
      sane PE32 header (Machine 0x14C, 3 sections, optional-header magic 0x10B, ImageBase
      0x10000000, SizeOfImage 0x1C000, EP 0x1AB00).
    - Two dwords do NOT decode to valid magic: logical 0 (0x0090A808 instead of 0x00905A4D) and
      logical 0x108 (0x11EDFB9B instead of "PE\0\0"). The signatures were erased on purpose; the
      loader parses fields by offset and does not need them.
  Verification (all passed):
    (1) Adler-32 of the 39,670 decoded bytes at stage-2 offset 0x400 = 0xD8446DB7 = the c_adler
        stored in the UPX header (chance of coincidence ~ 2^-32).
    (2) NRV2B decompression consumed exactly 39,670 of 39,670 bytes and produced exactly 102,159
        bytes = u_len; Adler-32 0x51C74D4C = stored u_adler.
    (3) The PEiD-format DB identifies the decoded stage-2 entry point as a UPX DLL stub.
  The constants (0x0A0A0082, C1, C2, 0xDC, array base) are probably per-build parameters; hence
  the exact-build marker rule in section 13.

6.11 Metadata anomalies / forgery indicators  [DATA][INF]
  - Stage-1 TimeDateStamp 2000-10-07 predates the family's first public appearance (Nov 2008)
    by ~8 years. Linker version 7.0 is hard to reconcile with the Visual C++ 6.0 DLL start-up
    signature at the entry point and with the use of msvcrt.dll (VC6-era CRT). Combined with the
    zeroed Rich header and import descriptors lacking an OriginalFirstThunk (MSVC linkers
    normally emit it), the header looks post-processed. Treat all compile-time metadata as
    unreliable.
  - Stage-2 header copy: TimeDateStamp 0x3F73A4C6 = 2003-09-26 02:30:30 UTC. The same DLL
    embeds zlib banners "deflate/inflate 1.2.3 Copyright 1995-2005", so it cannot have been built
    in 2003: this timestamp is false as well.
  - Stage-2 SizeOfHeaders is 0x1000 although the first section starts at file offset 0x400
    (non-standard; noted, not interpreted).
  - FileAlignment == SectionAlignment == 0x1000, DllCharacteristics 0, no debug info.

14. CONFIDENCE, LIMITATIONS, STATIC FOLLOW-UPS
================================================================================================
Confidence
  HIGH    The file is malicious; it is a three-layer wrapper; layers 2 and 3 are exact (two UPX
          checksums verified); packed / encrypted / obfuscated status; no anti-debug in stage 1;
          the worm behaviours read at instruction level (guards, hot-patch, installation, service
          registration, HTTP server, geo filter, downloader, payload-signature gate, timers),
          independently corroborated by capa 9.2.1 at function level (70 rules, every hit
          reconciled, section 9.1); stage-1 base relocation.
  MEDIUM  Conficker variant A attribution (strings and code vs public reporting, no hash comparison);
          the propagation, rendezvous and UPnP components (function-level evidence only);
          the DNS negative-cache explanation of SRI's 5-minute figure (inference).
  LOW     The origin of the 7,424-byte block and of the HTML trailer: both are characterised (dead
          data, uniformly random / generic HTML) but not explained.

Limitations
  - Static only: nothing was run, so no behavioural or network observation backs any statement.
    The analysis VM was used for static tools only (capa, DiE) and the sample was never executed.
  - Stage 3 was rebuilt and disassembled, but only part of it was read at instruction level; the
    exploitation, payload-delivery and host-name-generation internals were deliberately not
    documented (flow document, scope note).
  - capa finds nothing in the file as received and under-reports stage 3: no rule covers the RSA
    code, the domain generation, UPnP / SSDP or the SMB / RPC client (9.1). Two of its hits (RC4
    PRGA) are false positives. FLOSS was intentionally not run (its decoding stage emulates code).
  - The public-reporting cross-check was read second-hand through a web-fetch helper (primary
    USENIX URL unreachable); SRI's statements were not re-verified against the primary PDF.
  - Per-build parameters of the stage-1 encoder mean sibling samples will need their constants
    re-derived; the Stage1 YARA rule is structure-based for that reason.
  - kido.zip was skipped at the user's request (the user states it is the same sample).

Suggested static follow-ups
  1. Compare this build with other builds of the same wrapper (7,424-byte block, HTML trailer,
     keystream constants): differences would confirm that they are per-build junk / parameters.
  2. Look the hashes up (sample, PE-image portion, imphash, derived layers, RSA modulus hash) and
     compare stage 3 with reference Conficker.A samples.
  3. Use the rebuilt stage-3 PE (9.1; sha256 19f2274c...b07d49, file offset == RVA, so it lines up
     with every RVA in the flow document) in a disassembler to read the parts that were only
     summarised: propagation, name generation, UPnP. It is a live worm DLL: keep it non-executable.
     A copy remains in the session scratch folder only; it can be rebuilt from the sample (Appendix A
     recipe plus the PE-building step of 9.1) and a non-executable copy can be saved into the project
     folder on request. The copies on the analysis VM were deleted.
  4. Optional dynamic confirmation (NOT done): the DNS negative-cache cadence of the downloader
     (flow document 3.9), the offline CPU spin, and the runtime artefacts (service key, dropped DLL
     name, mutex, HTTP port). The analysis VM as configured is bridged to the home LAN and the
     router. The worm probes private ranges and asks UPnP gateways for port mappings, and a
     snapshot revert cannot undo changes made outside the VM (a router port mapping, packets that
     reached other hosts). FakeNet-NG 3.5 on the VM, with its default.ini, does not divert TCP 139
     or UDP 67/68/137/138/443/1900/5355 (NetBIOS session service, NetBIOS name / datagram service,
     SSDP), so those probes would still reach the LAN. A host-only network should come first; with

  # Stage 1 -> stage 2
  u32(off)  = little-endian dword of kido.sample at file offset off
  BASE = 0x6088            C1 = u32(0x6068) = 0xC41972EB      C2 = u32(0x603C) = 0x86E61B46
  K    = 0x0A0A0082

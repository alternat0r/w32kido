# W32/Kido (Conficker A) — Visual C++ 2022 reproduction

`kido.sample` is a **32-bit Windows DLL** that is a **3-layer wrapper** around a
**Conficker (a.k.a. Kido / Downadup A) worm** DLL:

```
kido.sample (stage 1)        obfuscated reflective loader / "crypter"
  └─ decodes + maps by hand   (exact position-dependent XOR keystream)
        └─ stage 2            UPX-packed DLL (NRV2B)
              └─ UPX stub decompresses
                    └─ stage 3            the Conficker worm (this directory's src/)
```

This directory is a **from-scratch behavioural reimplementation in C++** of all
three layers, built with **Visual C++ 2022 (MSVC v143, x86)**. It reproduces the
worm's execution order, API calls, and every behavioural constant recovered from
the sample by static analysis (see `../kido_static_analysis_report.txt`,
`../kido_program_flow_pseudocode.txt`, `../kido_worm_strings.txt`).

The sample and the reproduction were **never executed on the host** — the test
drivers below are meant to run on the isolated analysis VM.

## What the original is

| property | value |
|---|---|
| family | CONFICKER (W32/Kido, Downadup) variant A |
| PE | PE32 i386, GUI subsystem, no exports, ImageBase 0x10000000 |
| stage 1 | 42,496-byte encoded stage-2 in `.data`; XOR keystream `key[i]=((((i\|0x0A0A0082)<<1)^0xC41972EB)-0x86E61B46)`, block-XOR 0x37; MZ/PE signatures erased; maps stage-2 by hand (VirtualAlloc/LoadLibraryA/GetProcAddress/VirtualProtect) and calls its entry point with DLL_PROCESS_ATTACH |
| stage 2 | UPX-packed DLL (NRV2B-LE32, adler-verified); the stub decompresses the worm |
| stage 3 | the Conficker worm: 181 functions, MS08-067 class propagation, HTTP payload server, UPnP port mapping, domain-generation rendezvous, GeoIP + keyboard-layout Ukraine avoidance, svchost "netsvcs" persistence, System Restore reset, netapi32 hot-patch |

### Behaviour (reproduced in `src/worm/`)
1. **DllMain** (`kido_guards.cpp`, sub_06B34) — `DisableThreadLibraryCalls`;
   Ukrainian keyboard-layout check (LANGID 0x0422 → do nothing); single-instance
   mutex `Global\<CRC32(computer name)>-7`; second instance → `MoveFileEx`
   delete-at-reboot.
2. **main thread** (`kido_main.cpp`, sub_06847) — seed C PRNG (thread id ^ pid ^
   perf counter ^ tick count); hot-patch `netapi32!NetpwPathCanonicalize`;
   [Win2000] inject `services.exe`; if not `*.dll` self-install into `system32`
   + register svchost `netsvcs`; read own image + `LockFile`; `WSAStartup`;
   ntdll language id; start HTTP server; geo database + network worker; 30 min;
   scareware downloader; rendezvous loop (3 h online / 60 s offline).
3. **HTTP payload server** (`kido_http.cpp`, sub_0C334) — bind a random port
   1024–9999 (PRNG reseeded from the volume serial), open the firewall port
   (COM `INetFwPolicy` / stop SharedAccess), answer inbound requests
   `Content-Type: image/jpeg` with the worm's **own file image** so a
   compromised peer can fetch the payload.
4. **Network worker** (`kido_net.cpp`, sub_08A08) — public-IP lookup (3 sites),
   UPnP `AddPortMapping`, throttled MS08-067 class propagation over
   `\\host\IPC$` → srvsvc/browser pipes, directing a hit to fetch from the HTTP
   server.
5. **Crypto** (`crypto.cpp`) — SHA-1, RC4, CRC-32, RSA-1024 (e=50001)
   payload-signature gate with bignum modular exponentiation.
6. **Stage-1 loader** (`src/wrapper/loader.cpp`) — decodes the embedded
   stage-2 with the exact original keystream, maps it reflectively, resolves
   its imports, applies base relocations, sets section protections, and calls
   the UPX stub with `DLL_PROCESS_ATTACH`.

## Build
```
build.bat
```
(or double-click). Produces, in `build/`:
* `kido_worm.dll` — the worm (stage 3)
* `kido_stage2.dll` — the worm UPX-`-9` packed (stage 2)
* `kido_stage1.dll` — the reflective loader embedding stage-2 with the exact
  original keystream (stage 1) — **this is the drop-in reproduction of
  kido.sample**
* `test_crypto.exe`, `decode_test.exe`, `worm_load.exe`,
  `inject_test.exe`, `inject2_test.exe`, `load_test.exe`

The build is size-optimised and PDB-free: `/O2 /Oy- /GF /Gy`, `/MD` dynamic CRT
(the original worm dynamically linked its CRT — `MSVCRT.dll` in its import
table), `/OPT:REF /ICF`, `/DEBUG:NONE`. `/MD` is required: a static-CRT `/MT`
build balloons the worm to ~167 KB and no longer fits the 42,496-byte stage-1
`.data` embedding layout.

Two original PE identities are reproduced exactly: stage-1 `ImageBase
0x10000000`, GUI subsystem, and the original TimeDateStamps (stage 1
`0x39DF5AFB`, stage 2/worm `0x3F73A4C6`).

### Notes on modern-OS behaviour
The worm targets Windows 2000 / XP / 2003. Two things are handled for modern
Windows:
* **Firewall / SharedAccess** — the legacy firewall COM API (`INetFwPolicy`)
  and the `SharedAccess` service are XP/2003 mechanisms; the worm applies
  them only on those OSes (on Win7+ the firewall moved to the netsh/FWPM
  provider and the legacy COM interface is deprecated).
* **`ObtainUserAgentString`** — called with its modern 3-arg stdcall signature
  `(DWORD, LPSTR, DWORD*)`. (The old XP 4-arg wide-char form no longer exists;
  calling it as 4-arg leaves a 4-byte stack skew that corrupts the return
  address.)

`test_crypto.exe`, `decode_test.exe`, the worm `DllMain`/main thread, the HTTP
payload server (bind + GET of its own image), and the single-instance mutex are
all confirmed working on the analysis VM (Windows 10, 32-bit path).

## What was NOT reproduced
* Stage-1's *heavy obfuscation* (scattered basic blocks, ~50 decoy API calls,
  90 junk x87 ops, opaque constants, zeroed Rich header) — these are
  **indicators, not behaviour**; the decode/map/hand-off semantics are exact.
* The exact **MS08-067 packet/shellcode construction** — kept at the
  behavioural level (per the analysis scope note); the observable artefacts
  (SMB sessions, RPC binds, the HTTP fetch directive) are reproduced.
* UPX version — the reproduction re-packs the worm with UPX 5.x (NRV2B),
  which yields a functionally equivalent stage-2 (same NRV2B-LE32 scheme,
  adler-verified); the original used a UPX 1.x stub.
